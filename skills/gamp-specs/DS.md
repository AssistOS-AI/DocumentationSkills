# GAMP Specs Design Summary

## Introduction

This skill defines how a project creates and maintains its README, HTML documentation, agent guidance, design specifications (DS files), and coding-style reference. It preserves the former `gamp-structure` behavior and adds synchronization rules for repositories that contain a catalog of skills.

## Core Content

The skill ties `README.md`, `AGENTS.md`, `docs/`, and `docs/specs/` together. It requires README instructions that let a new user install, configure, start, integrate, or use the project through every path that applies. Across all documents, it requires concrete language, verified terminology, a reading order that introduces concepts coherently, and feature descriptions that explain purpose before implementation. An HTML page that introduces new project-specific terms or concepts must provide a `Definitions` section for them; a page without new terminology does not require that section. Every occurrence of a defined term outside that section must link to its local definition anchor or to the exact canonical definition on another page, while useful inline explanations may remain. Documentation must represent the final product contract rather than the repository's intermediate development state: user-facing pages must not report missing code, unfinished work, or “planned” interfaces. DS files express requirements, rationale, limitations, assumptions, and unresolved boundaries as declarative statements. Existing question-and-answer design material is converted into statements in `Core Content` or another subject-specific section. Every project receives one gap-free `DS0xx-main-behavior.md` whose content comes from `detect-main-behaviors` and is limited to the central purpose, primary paths, project-spanning behaviors, essential interfaces, active direction-changing consequences, and architectural skeleton. Comparisons must identify a practical difference between real alternatives; they must not decorate a direct statement with an obviously undesirable alternative. HTML documentation must use the available page width without a fixed maximum-width constraint on the main text panel, with compact responsive padding around and inside that panel. Its primary navigation must use stable menu groups with submenus, may preserve categories with zero or few real links, and must close open submenus on outside interaction. Diagram guidance is centralized in a dedicated reference and requires titled figures with italic subtitles, meaningful containment of related actors, a limited actor count, and consistent category-based colors and typography. The skill also defines three-digit DS names, gap-free numbering, English persistent content, diagram assets under `docs/assets/`, and declarative DS contracts with no generated question-and-answer section.

When a target project uses WebSkel, GAMP guidance must require `webskel-ui-engineering` and carry its verified coding rules into `DS001-coding-style.md`. The target documentation must give WebSkel-specific terms verified inline definitions or exact links to their local or canonical definition entries.

## Conclusion

Future project bootstraps must use this skill as the starting point for repository documentation rules. Changes to project layout, DS policy, coding-style rules, reader onboarding, or documentation synchronization must be reflected here first.
